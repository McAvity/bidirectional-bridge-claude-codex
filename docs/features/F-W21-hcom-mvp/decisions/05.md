# Decyzja 05 — integracja hcom z feature-execute

Status: approved — rozszerzenie zakresu wykonania, 2026-11-10.
Użytkownik po propozycji integracji odpowiedział: „Dobrze tak zróbmy.”
To zgoda na implementację przedstawionych sześciu zmian, test rzeczywistego skilla,
niezależne review, zwykłe korekty i lokalne commity. Propozycja odbioru04 nie została
zaakceptowana: wracamy do wykonania szerszego, uzgodnionego wyniku na branchu F-W21.

Zakres: jawny trwały wybór bridge/hcom, hcom-loop w feature-execute, wspólne reguły
wykonawcy/dostawy Git, lokalny stan rundy/sesji, routing feature-flow i przewodnika,
generowane paczki workflow oraz pilot przez skill z korektą i wznowieniem koordynatora.
Jeden feature, jeden worker Claude, jeden lokalny repo/worktree. Bridge pozostaje
domyślny tam, gdzie był wybrany; nie ma automatycznego fallbacku czy migracji aktywnej
sesji. Bez pełnego recovery, multi-worker, publikacji, push/merge i zmiany pinów
istniejących projektów. Prosty pomocnik zapisu stanu może zastąpić powtarzane ręczne
edycje JSON; nie uruchamia modeli i nie jest drugim kontrolerem.

Walidacja zachowuje niewykorzystany budżet zgody03: jeszcze jedno podejście i dwa
prompty wykonawcy (łącznie maks.2/4), 10 minut/rundę, maks.30 minut nowej części
modelowej. Istniejące konto, bez nowych kluczy/zakupów i bez pomijania uprawnień.
W razie wyczerpania budżetu zachować stan i jawnie wskazać brakujący dowód.

Plan rozszerzenia podlega niezależnemu review przed implementacją. Istniejąca zgoda
użytkownika obejmuje wykonanie tego zakresu po technicznym PASS; nie wymaga powtórzenia
Gate1. Końcowy odbiór rozszerzonego featura pozostaje Gate2 po realnym teście/review.
Wybrany stary zestaw steruje pracą nad F-W21; zmieniane nowe skille są produktem.
Obcy MCP potwierdzony ponownie: brak mutacji. Test nowej paczki tylko w osobnym repo.
