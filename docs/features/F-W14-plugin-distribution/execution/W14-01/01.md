## Problems and resolutions

**Running a host far enough to start MCP servers without spending a model call.**
Codex starts plugin MCP servers as part of the turn, so `--help`-level inspection
proves nothing. Resolved by configuring a provider whose `env_key` names a
variable the probe deliberately deletes: the session boots, starts MCP, and the
first request fails locally in ~0.25 s having contacted nothing. The Claude side
points `ANTHROPIC_BASE_URL` at a local stub answering HTTP 400; the CLI's own
result frame then reports `total_cost_usd = 0`, zero tokens and
`api_error_status = 400`, which each probe asserts.

**A recorder that cannot use environment variables.** The first recorder took its
output path from the environment and produced an empty file under Codex, which
initially looked like "MCP never started". The actual cause was the finding
itself: Codex strips the environment of a plugin MCP server to an allowlist. The
record path moved into `argv`, and the stripped-environment behaviour became
probe evidence rather than a probe bug.

**A false positive from `PWD`.** An early interactive check showed
`env_vars: ["PWD"]` delivering the correct worktree, suggesting the problem was
solved. It was an artefact of running the check from a shell already sitting in
that directory. Re-running with the parent's `PWD` controlled independently of
the launch directory showed `PWD` is forwarded verbatim from the parent — absent
without a shell, stale from an unrelated checkout, and divergent under
`codex -C`. The probe now covers all four parent states, and the conclusion is
negative.

**Host results.** Full interpretation is in
[`evidence/W14-01/README.md`](../../evidence/W14-01/README.md); the three
feasibility questions resolve as:

1. **Plugin MCP workspace — negative.** A Codex 0.154.0 plugin MCP server runs
   with `cwd` inside the version-pinned plugin cache, an environment stripped to
   `HOME, LANG, LC_ALL, LOGNAME, PATH, SHELL, TERM, USER`, and an MCP handshake
   with no `roots` capability and no project path. `env_vars: ["PWD"]` only
   re-exports the parent's `PWD`. Eight cases, all model-free. Resolving a
   worktree root from a *correct* `PWD` does work for paths with spaces, launches
   from a subdirectory and external Herdr-style worktrees — the resolution is
   fine, the input is missing.
2. **Delegated Claude instructions — positive.** `claude -p --plugin-dir <dir|zip>`
   loads a plugin for one session with an empty `CLAUDE_CONFIG_DIR` and no
   project `.claude/`, starts its MCP server with the project `cwd` and exports
   `CLAUDE_PROJECT_DIR`/`CLAUDE_PLUGIN_ROOT`. A no-`--plugin-dir` control loads
   zero plugin skills, so the positives are not an ambient install. Coexists with
   `--disallowed-tools`, so the further-delegation lock is unaffected.
3. **Cache update and restart — negative on Codex, positive on Claude.**
   Installing a new Codex plugin version **deletes** the previous version's cache
   directory; a restart then moves runtime and instructions together to the new
   version, so nothing is *mixed*, but a pin inside the cache stops resolving.
   Claude Code retains both versions and asks for a restart. A wave12-style
   runtime kept outside the plugin cache is byte-identical after both a plugin
   update and a plugin removal.

Supplementary: under `codex exec`, an inherited `[mcp_servers.bridge]` block whose
launcher is missing does not abort the session with `required = true` or `false`.
**The interactive TUI was not tested** and no claim is made about it.

**Limits of this evidence.** One host, one OS, one version of each client. No
model ran and no real delegation was performed, so nothing here supports a claim
about end-to-end Astra → Claude behaviour. The Codex vendor plugin documentation
at `learn.chatgpt.com/docs/plugins` could not be fetched in this round (the fetch
tool was not authorised), so Codex manifest statements rest on the installed CLI
and the local `plugin-creator` reference; the Claude Code plugin and marketplace
references were read and agree with the observations. The unit tests in
`tests/plugin-probes/` are fixture checks of the harness only and are not host
evidence.

**Isolation.** Every probe ran with `CODEX_HOME`/`CLAUDE_CONFIG_DIR` inside
`~/tmp/w14-01-probes/`; `probe_lib.assert_isolated()` aborts on any path inside
`~/.codex`, `~/.claude` or `~/.config/claude`. The personal profiles and the
active runtimes are unchanged. Committed results are redacted: the home prefix
becomes `<home>` and `PATH` becomes an entry count.

(`probe_missing_runtime_startup.py`) was added beyond the three the plan names,
because the package design depends on whether a half-prepared worktree can still
start Codex. It is labelled supplementary and carries its own scope limit.

**Proposals, not decisions.** Two contracts are proposed for coordinator review:

- `contracts/01-package-and-bootstrap.md` — one generated source, two package
  payloads and two marketplaces in this repository; the bridge MCP server stays
  project-scoped because finding 1 makes a plugin-hosted server unable to find
  its workspace; a portable project declaration separate from local state; the
  `bridge-setup` skill replacing the manual `init`; `--plugin-dir` for the
  delegated executor; the pinned runtime kept outside the plugin cache because of
  finding 3. It records the rejected late-bound plugin MCP alternative with the
  concrete unverified dependency that rejects it, and four open questions.
- `contracts/02-wave13-metadata.md` — one optional, fully nullable
  `distribution` object added to whatever wave13 emits. It is explicitly **not
  merged** and assumes nothing about wave13's in-progress shape; wave13 keeps
  ownership of logging, retention and export.

**Proposed change to an existing document, not applied.** Contract 01 questions
whether the managed `[mcp_servers.bridge]` block should remain committable as
`docs/setup-layout.md` allows, since a new worktree inherits it without the
gitignored runtime symlink. `docs/setup-layout.md` is unchanged in this round.
