### 2. AC-03 was still not met — the step back

`decide()` refused a worktree with no local record, so every inherited worktree needed a manual
`setup`; attempt 01's tests hid that by calling `setup` there themselves. That is the third time the
same requirement came back, so this attempt stepped back rather than patching again.

A worktree inherited from an enabled project is **pristine** by construction. The launch gate now
lets it serve and registers what its first mutating call must write; the server runs that once,
**inside the guarded mutation, after the native identity guard has authorised the caller** — the
existing boundary in `runTool`. No second setup facade, no hand-written project code, no
per-worktree command and no extra restart.

Placement matters and was corrected during this attempt: the hook first ran *before* the guard,
which materialised state for a call carrying no native context. It now runs inside
`runMutation`/after `authorize()`, and a test proves an unauthorised call leaves the worktree
byte-identical.

Kept: pure handshake and reads, foreign refusal, and launch refusal for divergent, invalid, disabled
or partial state. New: `SETUP_STATE_PARTIAL` for a half-removed local setup, which is refused rather
than re-created.

Known limit, recorded rather than hidden: `bridge_manager_resume_instance` and
`bridge_manager_takeover` drive the guard themselves and do not trigger materialisation.
