## Disposition

### W14-R2-06 — same-worktree concurrent first use could not progress

**Reproduced** with the reviewer's script at `6b483b2e…`: both processes returned
`INTERNAL/ACTIVE_SESSION` naming the other's `state-open` descriptor, and neither wrote a record.

**Cause.** Both entry processes complete the handshake, so both hold the worktree's database open.
The setup plan's process scan then sees the *other* bridge process and refuses — even though the
native identity guard had already admitted exactly one of them to its critical section.

**Fix.** `planChange` gains `insideGuardedMutation`, used only by the materialiser. It drops the
`bridge-mcp`/`state-open` veto for a caller that is already inside the guard, because the guard is
the authoritative serializer there: a second caller is refused as a foreign manager. Every other
refusal is unchanged, and ordinary `init`, `update` and `rollback` from the CLI keep the full scan,
including the `ACTIVE_SESSION` refusal while a server is serving — re-asserted by a test.

**Proven:** one `OWNER`, one `MANAGER_FOREIGN_THREAD`, a single record naming this worktree, no
leftover journal, and both processes still answering reads.

### W14-R2-07 — interrupted automatic preparation needed a manual setup

**Reproduced** with the product's own fault injection: exit `-9` after the first write, leaving
`pending.json`; the restart refused `SETUP_STATE_PARTIAL`.

**Fix.** The journal now records the worktree and runtime it belongs to, so a resume can *prove*
ownership rather than assume it. The launch gate serves a worktree whose partial state is provably
its own interrupted apply and completes it at the next authorised mutation, through the existing
resumable journal. A journal naming another worktree, an unreadable one, one for a different
runtime, or one written before the journal recorded its workspace stays refused with nothing
written. No manual setup, no extra restart, no adoption of foreign state.

**Proven:** crash → restart serves reads with a byte-identical tree → the next authorised mutation
succeeds, the record names this worktree and the journal is gone; plus three refusal cases that
leave the file byte-identical.

### W14-R2-08 — the plan installed a runtime

**Reproduced:** `applied=false` with `runtime_installed_now=true`. Worse than reported: with no
`CLAUDE_CODEX_BRIDGE_HOME` set, the dry run installed `0.2.0-6b483b2e1a23` into the operator's real
`~/.local/share/claude-codex-bridge/runtimes/`. I removed exactly that runtime after
hash-confirming it was the one the dry run created; the supervisor runtime `0.2.0-860e2e77d95f`
beside it was not touched, and no `sources/` cache was created. This is recorded rather than
quietly cleaned up.

**Fix.** Acquiring a source and building a runtime are writes under the bridge home and now happen
only under `--yes`. Without it, a worktree whose pinned runtime is absent gets an honest plan naming
the commit that would be installed and no invented file diff; when the runtime is installed the full
reviewable per-file plan is produced as before.

**Proven:** the dry run creates neither the bridge home nor anything in the project, and the
per-file plan is still produced when the runtime is present.
