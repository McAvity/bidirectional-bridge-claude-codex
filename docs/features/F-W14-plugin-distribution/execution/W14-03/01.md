## Problems and resolutions

**The environment is stripped for a project MCP server too.** The first host hand-over attempt
served nothing because `CLAUDE_CODEX_BRIDGE_HOME` never reached the server. The managed block now
names that variable and `XDG_DATA_HOME` in `env_vars`; both are names, not values, so the block
stays portable.

**A space in a project path broke the entry point.** `new URL(...).pathname` percent-encodes, so
`a project with spaces` became `a%20project%20with%20spaces`. Fixed with `fileURLToPath` in the
entry point and the launch gate. It only surfaced because every test worktree has a space in its
path; the earlier manual end-to-end run did not.

**Two test-harness facts, not product facts.** The runner puts `node_modules/.bin` first, so a
child `codex` resolved to the pinned development dependency 0.147.0 and the compatibility guard
correctly refused it; and vitest's module runner cannot dynamically import files outside the
project root. The harness now gives children a client-like `PATH` and exercises the launch gate
through the committed entry point in a child process — which is the production path anyway.

**The release pin cannot be fetched from the public repository yet**, because this branch is not
published. Acquisition from `--source`, `CLAUDE_CODEX_BRIDGE_SOURCE` and the local cache is what
the tests use; the fetch path is implemented and unexercised, and is recorded as such.
