## Problems and resolutions

**The dispatcher could not see its own installation.** The first host hand-over test failed:
Codex started the dispatcher but it served the facade instead of the pinned runtime. The cause was
not a bug in the routing — W14-01 had measured the stripped environment for *plugin* MCP servers,
and the same stripping applies to a **project**-scoped server, so `CLAUDE_CODEX_BRIDGE_HOME` never
arrived. Resolved by naming that variable and `XDG_DATA_HOME` in the managed block's `env_vars`.
Both are variable names, so the block stays free of machine paths, and the test now observes the
hand-over with the correct absolute `--workspace`.

**Project configuration is gated twice by the host.** While building the bootstrap, two further
host facts appeared: Codex reads a project `.codex/config.toml` only for a project trusted in
`CODEX_HOME/config.toml`, and reads none at all when started in a subdirectory. Neither is
worked around. The trust decision is surfaced in the skill and the documentation; the subdirectory
case is documented as unsupported rather than papered over.

**Reference rewriting was initially too blunt.** The first generator rejected its own output,
because the thin entry skill legitimately names `<instructions.root>/.agents/skills/` — an
absolute reference into the installed runtime, not a dead checkout-relative link. The scanner now
distinguishes anchored references from bare ones and checks every occurrence, not the first.

## Deviations and proposals

**Design choice within the review's allowance.** The review offered a portable project MCP
dispatcher or a static-catalogue plugin facade. Both were taken, in the only combination the host
supports: the dispatcher is the project-scoped server (a plugin-hosted one cannot learn its
workspace), and the facade is what that dispatcher serves when the pinned runtime is absent — with
a **static** catalogue, so nothing depends on `tools/list_changed`.

**Ordinary implementation choices.** Package directory names (`plugins/bridge-codex`,
`plugins/bridge-claude`) follow the documented convention for both hosts; the committed project
files live under a single `.bridge-project/` directory; `required = false` in the managed block so
a machine without the runtime can still start its client and install one.

**Contract changes, applied.** `docs/setup-layout.md` gained the wave14 per-worktree rows, the
`.bridge/bootstrap.lock` entry, the distribution metadata section and the three host properties.
Revision 1's claim that the wave12 journal already covered concurrency is withdrawn and replaced by
the lock, the revalidation and their tests.

**No new product decision** was taken; everything above is inside `decisions/01.md`.
