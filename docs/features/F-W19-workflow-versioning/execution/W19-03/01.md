## Problems and resolutions

- **Bez kompozycji binding byłby martwy albo psułby wszystkie dotychczasowe testy.** Wybrano jawny
  tryb: binding działa po `cp.enableWorkflowBinding(port)`; bez tego zachowanie sprzed bindingu,
  status `binding: "not-configured"`, operacje workflow i każde `workflow_identity` → `UNIMPLEMENTED`.
  Włączenie w procesie MCP należy do W19-04 (plik poza zakresem tej rundy).
- **Numer próby rundy**: orchestrator numeruje pierwszą próbę od 0; admisja zapisuje próbę 0 w
  transakcji tworzącej task (wiersz próby powstaje później), dlatego osobna tabela zamiast kolumn.
- **Intent i commit switcha** są w SQLite jedną transakcją; punktem przerwania pozostaje projekcja
  pliku (przed i po zapisie). Model referencyjny W19-01 rozdziela te kroki — kontrakt to opisuje.
- **Switch przy BLOCKED/FAILED** odmawiany, aby odtworzenie zawsze działało pod workflow, z którym
  task ruszył; inaczej replay mógłby przyjąć nowszy wybór.
- **Profil legacy**: klucz tabeli to rzeczywisty digest; test odtwarza zestaw 0.7.0 z commita
  `6ed9a45` w Git (`git archive`) i potwierdza równość z kluczem `8c05792a…`.
- Trzy istniejące testy `tools.test.ts` przypinały dokładną listę argumentów narzędzi resume;
  `workflow_identity` to zamierzona zmiana kontraktu (R19-C02), oczekiwania zaktualizowano. Dwa
  testy przypinały numer schematu 6 (`closure-schema`, `feature-closure` „forward guard”); zamienione
  na `schemaVersionSupported` (+1), sens testów bez zmian.
