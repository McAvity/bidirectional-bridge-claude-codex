## Format and correlation (the decision this round had to make first)

Format `claude-codex-bridge.log/v1`, JSONL, one file per process under `<worktree>/.bridge/logs/`,
mode `0600` in a `0700` directory. Every record carries the schema id, so a rotated or truncated
tail still identifies its own format. Fields: `ts` (UTC), `seq` (per-process counter), `mono_ms`
(monotonic since process start — the wall clock is not the only ordering evidence), `pid`,
`instance`, `role`, `source`/`runtime`, `workspace`, `op`/`event`, `tool`, `outcome`/`code`/`phase`,
`request_id` (JSON-RPC id), `duration_ms`, `feature_id`/`task_id`/`attempt`, and a `details` map of
at most 12 clamped scalars. Unknown values are `null`; nothing is inferred. Full documentation:
[docs/diagnostics.md](../../../../diagnostics.md).

Correlation without content: the JSON-RPC request id joins one client call, `task_id`/`attempt`
join the database, `instance`/`pid` separate two processes of one worktree, and a manager-chosen
idempotency key and the native thread id appear only as 12-hex SHA-256 prefixes. Executor deadline
(`details.deadline_ms` of the call) and the MCP client timeout stay separate facts, `num_turns` is
never compared with `max_turns`, and telemetry is never called a charge.

## Authorized write points

Two, both already chokepoints of the isolation protocol:

1. **The identity guard** (`IdentityRuntime`). `arm()` is called only after an authorized
   operation *committed* — for an asynchronous round, after its reservation committed — and it is
   the only place that creates `.bridge/logs/`. It then writes `process.start` (restating the
   process facts, with the count of records produced before arming) and `manager.authorized`.
2. **The MCP tool boundary** (`runTool`). One `tool.call.finished` record per call with outcome,
   stable error code, `guard`/`handler` phase, duration and correlation fields.

Plus the process lifecycle in `serve()`/`close()`: `process.serving`, `process.stop`,
`manager.instance.detached`, `adapter.dispose.failed`, and the logger's own `log.rotated`,
`log.retention`, `log.close`.

Consequences, which the tests pin: process start, a handshake, reads, `bridge_manager_status` and
a refusal in a never-authorized process create no directory and no file; before binding there is
no local buffer at all (a buffer would need its own ownership, which §1 asks not to invent) —
those records are counted as `deferred_records` and exist only in the bounded stderr warnings.

## Defaults and configuration

Per worktree: record 8 KiB, file 4 MiB, total 32 MiB, 16 files, 14 days; `BRIDGE_LOG=off`
disables. Overrides come from the environment the launcher was started in
(`BRIDGE_LOG_MAX_RECORD_BYTES`, `BRIDGE_LOG_MAX_FILE_BYTES`, `BRIDGE_LOG_MAX_TOTAL_BYTES`,
`BRIDGE_LOG_MAX_FILES`, `BRIDGE_LOG_MAX_AGE_DAYS`) — one surface, no daemon, no second
configuration file inside `.bridge/` (which would also be an unexplained state entry). Every value
is range-checked; an unusable one keeps the default and produces one bounded warning, so the
limits are always finite.

Retention deletes, oldest first, only files matching this bridge's own name pattern; never the
file this process writes, never a file named by another instance's marker whose process is alive,
never a symlink (directory entries are classified without following them and log files are created
with `O_CREAT|O_EXCL`), and never the database, attempt evidence, packages or transcripts. A
deletion is recorded in-band as `log.retention` so a later export can show the gap.

## Deviations and deferrals

1. **No `doctor` diagnostics-status check.** §1 asks for a diagnostics status alongside the
   bounded stderr warning. Adding a check means adding a doctor code, and the stable code list
   lives in `docs/setup.md`, which is outside this round's write scope; documenting a code in one
   file and not the other would contradict `docs/setup-layout.md`. The status is therefore the
   bounded stderr warnings plus the in-band `log.rotated`/`log.retention`/`log.close` records
   (which carry failure, rotation and deletion counts). The check belongs with W13-02/03, which
   already touches `doctor` for the export.
2. **The EOF shutdown gap was not fixed.** §1 and the plan's validation section say to assess the
   evidence and not to widen the scope to every runtime defect found. The launcher's stderr shows
   no shutdown line on stdin EOF, so the sequence does not run; this round records the gap and
   documents it instead of changing the runtime's shutdown behaviour.
3. **`BridgeServerOptions.instanceId`** was added so the log and the manager identity name the
   same instance. It is optional and defaults to the previous per-process generation.

## Limitations

1. Model-free evidence only: the real launcher and a synthetic executor. This is not real-agent
   evidence, and AC-01…AC-03 coverage is claimed for these scenarios, not for a live pilot.
2. Records produced before arming are only in the process's stderr, which the bridge does not
   capture; an export must report them as unavailable.
3. A hard kill loses the final records and leaves an `.active` marker until the next authorized
   process cleans it; a full disk or a missing permission produces gaps that appear as failure
   counts and warnings, not as silent success.
4. `phase` and the arming flag assume one guarded call in flight per process — the same
   assumption as one manager and one feature per worktree. Concurrent guarded calls in one
   process could mislabel `phase`; this mirrors the existing per-process guard state.
5. Retention protects another instance's file by checking that its recorded pid is alive; a
   recycled pid after a reboot could protect a dead instance's file for one cycle. It never
   deletes anything outside the log name pattern.
6. Redaction is an allowlist plus digests, not a guarantee: `details` values are clamped and
   stripped, but a manager that puts content into an identifier (a feature id, a task id) would
   put it into the log as well.
7. Integration, CI, independent review and feature acceptance are out of this round.
