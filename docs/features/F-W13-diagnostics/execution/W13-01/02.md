## R1-01 — refusals and reads wrote to the log after the process had been armed

**Cause.** Arming was per process and the two guard flags (`authorizedCall`, `armedThisCall`)
lived on `IdentityRuntime`, so every later `runTool` wrote a `call.finished` record regardless of
whether *that* call had been authorized — refusals, reads, and any call overlapping a running
round. Attempt 01 even asserted the foreign-thread record as expected behaviour, which was the
wrong contract: §1 "Izolacja przed zapisem" forbids a refusal or a read from writing anything
into a manager's state, whatever the process did earlier.

**Fix.** Write permission is now a per-request object (`CallAudit`), created by `runTool` and
filled in only by the guard:

- `IdentityRuntime.runMutation`/`runMutationAsync`/`dispatch` take it explicitly; the three
  `authorize()` paths (bootstrap, bound, worker passthrough) set it, and nothing else can;
- for an asynchronous call the pure precheck authorizes a legitimate replay that reserves
  nothing, and a denial inside the reservation transaction **revokes** that permission again, so
  a race between the check and the reservation is refused, not recorded;
- `bridge_manager_resume_instance` and `bridge_manager_takeover` drive the guard themselves and
  now pass the same per-call object through `ToolContext.audit`;
- `runTool` writes `call.finished` to the file only when the call was authorized. Otherwise it
  goes to a new bounded stderr sink (`DiagnosticsLogger.note`), with the same allowlisted fields
  — so a refusal is still diagnosable and still mutates nothing;
- a session superseded by a takeover stops writing: `IdentityRuntime.isActiveInstance()` is
  checked before the shutdown record, and `DiagnosticsLogger.revoke()` releases the descriptor
  **without** writing a closing record and without deleting even its own `.active` marker —
  cleaning that up is left to the next authorized process, whose retention already recognises a
  dead instance's marker as stale.

**Regressions.** `native-launcher.test.ts`: (a) after arming, a foreign thread, invalid metadata
and a read leave `stateFingerprint()` of `.bridge/` byte-identical, while the same refusals are
visible in the process's stderr; (b) the same three calls issued **while a synthetic round is in
flight** leave the `logs/` fingerprint unchanged; (c) a takeover by a second session leaves the
first session's log file byte-identical across its fenced call and its `SIGTERM` shutdown, with
`stopped writing: shutting down without being the active instance` on stderr and the new owner
recording its own authorized call. `seq` gaps are asserted against `log.close.details.deferred`,
so the records that exist only on stderr are accounted for rather than hidden.

## R1-02 — retention stopped recognising its own files at rotation 100

**Cause.** `FILE_PATTERN` allowed exactly two digits for the rotation index while `openNextFile`
generates `100`, `101`, … Past the hundredth rotation a file matched nothing, so retention
counted and deleted nothing.

**Fix.** The pattern accepts two to six digits; a process that would pass `999999` disables
itself instead of producing names its own retention cannot recognise.

**Reproduction (red → green), same code except the pattern.** New test
`keeps recognising its own files past the hundredth rotation`, using the reviewer's valid public
configuration (`maxFileBytes=65536`, `maxTotalBytes=262144`, `maxFiles=2`) and 115 rotations
driven through `record()`, with a second live instance's file protected:

- with the two-digit pattern: **fail**, `expected 18 to be less than or equal to 3` — exactly the
  18 files the review reported;
- with the fix: **pass**, at most 3 files (the current one, one retained, one held by the live
  instance), total ≤ 262144 bytes, and a file with a three-digit index still present.

## R1-03 — missing observation points and a stderr claim that was not true

**Cause.** Only `call.finished` was emitted, so a long round had no correlatable start, the
attempt's own end/timeout was only visible through the call's envelope, and evidence-write
failures were invisible. `record()` without a file merely incremented `deferred` and returned,
while the documentation and ledger 01 said those records reached stderr.

**Fix.** Observation at the real points, with small metadata and no payloads:

- `attempt.started` right after `attempts.start` in both execution paths (delegation and strict
  recovery), carrying agent, executor `deadline_ms`, turn ceiling, continuation/recovery flag and
  `resumed_from_attempt`;
- `attempt.finished` on success and on failure, with `termination_kind`, measured `runtime_ms`
  and `phase: "deadline"` when the executor's own deadline expired — never conflated with the MCP
  client timeout;
- `attempt.evidence.recorded` / `attempt.evidence.write_failed` around the single place an
  adapter stores termination evidence, by reference (file, bytes, kind): the stderr tail stays in
  the existing evidence store and is not duplicated;
- `attempt.telemetry.write_failed` for bookkeeping that fails after the runtime returned;
- `ControlPlane` gained an optional `logger` so these observations come from where they happen;
  it only writes records and never reads state from them;
- `DiagnosticsLogger.note()` and the `record()` fallback now actually print to stderr, bounded to
  20 lines per process followed by one suppression notice, after which records are only counted.
  `log.close` reports `deferred` and `noted`.

**Regressions.** `records an attempt from its start and never logs a call that overlaps it`
polls the log *while the synthetic executor is still running* and finds `attempt.started` with
the executor deadline, then asserts `attempt.finished` with `code: TIMEOUT`, `phase: deadline`,
`termination_kind: timeout` and an `evidence.recorded` pointing at `attempt-0.json`, with the
runtime's stderr text absent from the log. `records a refused validation of an authorized call,
and reports the gap it cannot see` asserts that a scope escaping the repository is recorded as
`INVALID_ARGUMENT` / `phase: handler` without the offending path, and that a call rejected by the
MCP input schema produces no record at all.

**Documented, not claimed.** MCP schema validation happens in the SDK before any bridge code
runs, so it cannot be observed; this is now gap 5 in `docs/diagnostics.md`, together with the
takeover gap (6) and the unchanged `doctor` status deferral (8), which the review allows to close
with W13-02/03.

## Limitations

1. Model-free evidence only: the real launcher plus the synthetic `fake-claude-cli` executor.
   Not real-agent evidence.
2. Unauthorized calls are diagnosable only from the process's own stderr, which the bridge does
   not capture, and beyond 20 lines per process only as counts in `log.close`.
3. MCP schema violations are not observable at all (gap 5).
4. A takeover ends the superseded process's log without a closing record and leaves a stale
   `.active` marker until the next authorized process cleans it.
5. The EOF shutdown gap of attempt 01 is unchanged and still covered by its test; the review
   accepted it as evidence rather than a defect to fix here.
6. Retention still identifies a live writer by a recorded pid; a recycled pid could protect a
   dead instance's file for one cycle.
7. Redaction remains an allowlist plus digests, not a guarantee: content placed inside a feature
   or task identifier would still be recorded.
8. Integration, CI, independent re-review and feature acceptance are outside this round.
