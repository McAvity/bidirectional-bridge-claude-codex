## Wymagane korekty

**R04-01 — envelope fail-open.** §5.2 akceptuje brak całego x-codex-turn-metadata na samym threadId; §5.3 akceptuje nieznaną/brakującą wersję jako strict-fallback. Klasyfikacja subagentów opiera się właśnie na usuniętym obiekcie, a źródłowy dowód guardian dotyczy0.154.0. Ownership musi wymagać poprawnego obiektu, obecnych zgodnych session_id/thread_id/_meta.threadId i wspieranego zweryfikowanego adaptera; brak/nieznana wersja nie może obchodzić kontroli. thread_source nadal opcjonalne — brak był obserwowany dla poprawnego roota. Spójnie poprawić E-01, NativeCallContext i native_corroboration (żadnego none dla zaakceptowanego ownership). Nie wymyślać wymogu wyłącznie interaktywnego CLI: użytkownik wybrał pierwszy uprawniony ownership caller, więc codex exec jako inny root nie jest sam w sobie luką guardiana. Flaga interaktywności też nie wybiera konkretnego managera spośród dwóch rootów.

**R04-02 — instancje i fencing.** §7 oraz R-02/D-06 zezwalają obu instancjom tego samego thread na mutacje, last_instance_id służy tylko diagnozie. Sprzeczne z decyzją06§2/3. SQLite serializuje zapisy, ale dwie kopie tego samego managera mogą kolejno wykonywać sprzeczne decyzje z różnych kontekstów. Przywrócić aktualną instancję+generację w autoryzacji. Opisać dokładny restart/attach/handoff bez tokenów custody, dwa równoczesne resume, clean detach/crash oraz zakaz samoczynnego odbierania władzy przez fenced instance. Parametry CAS nie są dowodem tożsamości — to nadal host context. Ordinary mutator nie może powodować ping-pong. Spójne SQL, przejścia, testy.

**R04-03 — nieautoryzowane usunięcie external --db i nieskuteczna reguła symlink.** Decyzja06§6 wymaga opisać ograniczenie archiwizacji istniejącego zewnętrznego DB, nie zakazać całej funkcji. Stwierdzenie §3, że użytkownik zażądał takiego zakazu, jest nieprawdziwe. Przywrócić kanoniczny jawny --db i protokół wyłączności per-DB/per-worktree (B lub równie konkretna rezerwacja), bez poszerzenia produktu. Kontrprzykład nawet dla nowego zawężenia: oba worktree mają .bridge symlink do tego samego katalogu S. Dla obu realpath(parent(db))==realpath(root/.bridge)==S, więc opisany predykat przepuszcza współdzielony katalog mimo obietnicy odmowy. Wykonany syntetyczny Node/fs test w /tmp dał [true,true]. Trzeba porównywać rzeczywistą tożsamość worktree/state, nie dwie ścieżki podlegające temu samemu przekierowaniu. Fresh DB canonical path ma działać bez tworzenia .bridge podczas odczytu. Archive poza repo zachować; externalDB nie przenosi się razem z .bridge i fresh-start wymaga nowego DB, bez usuwania starego.

**R04-04 — rezerwacja/utrata markera i awarie.** §4.4 najpierw tworzy A (nowy workspace_id), a dopiero później czyta C; §4.5 obiecuje odtworzenie A z C bez nowego ID. Ustalić jeden porządek: preflight istniejących danych przed publikowaniem rezerwacji, recheck pod wspólną blokadą. Przypadek „A absent/requestedDB absent/otherDB holds C” bez skanowania nie jest wykrywalnym warunkiem; np. można fail-closed na niepustym katalogu stanu bez wybierania DB, ale algorytm ma to powiedzieć konkretnie. Nie zalecać usunięcia reserving markera bez dowodu, że właściciel rezerwacji nie żyje i że C nie commitowało — crash po commit przed rename pozostawia reserving przy prawdziwym bindingu. Opisać stale-reservation recovery (bez zgadywania procesu), błędy przed/po DDL/commit, RACE dwóch różnych DB, zachowanie po błędzie pierwszej operacji. Rezerwacja techniczna nie jest manager ownership; nie może stać się cichą trwałą zmianą DB po błędzie operacji.

**R04-05 — otwarcie DB przed guardem i realna semantyka odczytu.** Bootstrap step3 otwiera dzisiejszy zapisujący konstruktor PRZED manager guard step4; dla konkurenta sameDB/wrongthread może więc zapisać DDL/schema_meta/journal zanim zostanie odrzucony. W ogóle brakuje równie konkretnej ścieżki write-open istniejącego bound DB po restarcie. Wskazać osobno schema init/migration i otwarcie już gotowego store, ochronę między precheck a właściwą transakcją oraz brak nieautoryzowanych zapisów także przy takeover.

Wykonany kontrprzykład Node24 node:sqlite: utworzono syntetyczne DB w WAL, tabelę i rekord, zamknięto writer; przed RO tylko probe.db. `new DatabaseSync(path,{readOnly:true}); SELECT` utworzył probe.db-wal i probe.db-shm. B-05/§4.3 „no file creation, byte-identical journal files” nie wynika z samego readOnly. Nie stosować immutable z pominięciem żywego WAL — to grozi nieaktualnym odczytem. Kontrakt ma opisać wykonalny spójny odczyt: brak ownership, migracji, reconcile/reap, domain/event writes jest bezwzględny. Jeżeli infrastruktura SQLite tworzy techniczne sidecary, trzeba to jawnie odróżnić od mutacji trwałego stanu/ownership i odpowiednio sformułować testy, zamiast obiecywać fałszywą fizyczną byte-identity. Preferować rzeczywisty no-write odczyt, jeżeli da się go zagwarantować z obsługą żywego WAL; nie tworzyć nowego instalatora ani snapshot produktu.
