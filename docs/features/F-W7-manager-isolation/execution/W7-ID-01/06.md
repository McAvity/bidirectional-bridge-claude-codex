### Contract experiments run in this round

Isolated scratch files outside the repository, Node **v24.15.0**, `node:sqlite`. These are
**contract experiments on decisive mechanisms, not product tests** and not the protocol itself.

1. **Instance-history schema.** With `PRIMARY KEY (epoch, instance_generation)` and a *non-unique*
   index on `(epoch, instance_id)`, the inserts `(1,1,I1)`, `(1,2,I2)`, `(1,3,I1)` all succeeded
   and all three activation rows were readable. The eligibility query
   `SELECT NOT EXISTS(SELECT 1 FROM manager_instances WHERE epoch=? AND instance_id=?)` returned
   `0` for `I1` and `1` for a fresh `I3`. This is the direct counter-check to the reviewer's
   reproduction, which showed revision 5's `UNIQUE(epoch, instance_id)` failing the third insert.
2. **Lock database semantics**, observed step by step: `new DatabaseSync(path)` with **no DDL**
   created a **0-byte** `state.lockdb`; `PRAGMA busy_timeout` then `BEGIN IMMEDIATE` succeeded on
   that schema-less database and produced a `state.lockdb-journal` **while the transaction was
   open**; a second process got `ERR_SQLITE_ERROR` (`SQLITE_BUSY`) while the holder lived; after
   `kill -9` the next contender acquired immediately with no cleanup; after that contender's clean
   `ROLLBACK` the journal was gone and only the 0-byte main file remained.

## Problems and resolutions — R06 dispositions

**R06-01 — history index prohibited explicit reactivation: resolved.** The reviewer's counterexample
is confirmed and reproduced from the other side (experiment 1): revision 5's
`UNIQUE(epoch, instance_id)` made the permitted sequence I1 → I2 → I1 impossible, because the third
activation row collided. §12 now keeps the append-only history keyed by
`(epoch, instance_generation)` and replaces the unique index with a **non-unique lookup index**,
with a comment stating explicitly why it must not be unique. Adoption eligibility moved from a
constraint to the EXISTS query of §7.1, so automatic adoption still refuses any instance already
seen in the epoch while explicit full-CAS handoff can reactivate a previously fenced instance and
preserve every row. Ordinary Class M by a historical or fenced instance remains refused. §7.1 also
defines the previously unspecified **same-instance H**: with a matching CAS it is an idempotent
no-op returning the current `(epoch, generation)` — no new row, no generation bump, no invented
session — and with a stale CAS it is refused like any other stale handoff. §7.2 gains the
reactivation and same-instance rows, and tests I-04/I-05 cover both.

**R06-02 — incomplete bootstrap state machine: resolved.** Two gaps were real. First, the temp file
written before the `link` carries a nonce that is not the *current* operation's nonce, so revision
5's exemption would have classified it as unexplained while §4.5 promised that death before
publication "always proceeds normally" — a genuine contradiction. §4.1 now classifies interrupted
protocol temps **by parsed content**: the name form must match *and* the content must be a
well-formed marker/owner record naming this worktree's root and git dir, in state `reserving`, with
the nonce embedded in its own name; a name pattern alone is explicitly not evidence, and a
malformed, self-contradictory or foreign temp fails closed like any unknown file. Such a temp is
inert, blocks nothing, and may be removed **only** under the critical section when its nonce
matches neither published record and no binding references it — no arbitrary deletion, and no
promise of recovery for state that is deliberately rejected. Second, dispatch is now explicit
(§4.4): **Mode 1** unbound bootstrap publishes a reservation; **Mode 2** bound operations —
takeover, handoff, migration and ordinary M — **skip reservation publication entirely and mint no
new nonce**, reusing C's identity and `reservation_nonce`; **Mode 3** marker-only repair is a
sub-step of an authorized Mode-2 call, executed **after** identity/instance validation and before
the operation, so a foreign thread or fenced instance repairs nothing and leaves incomplete markers
untouched. `recovery_needed` is a concrete precheck predicate, reported by Class R (§4.3) and never
acted on by startup or reads. §4.5 now traces every case the review listed: missing `.bridge`,
failed operation, death before temp, death after temp before link, death after one link, death
after the main-database commit, ordinary M on incomplete markers, foreign M, and explicit H/T.
Unknown unrelated state still fails closed, C and existing history are never modified, and no
arbitrary database is scanned for identity.

**R06-03 — lock initialization and filesystem guarantee: resolved.** Revision 5 created L with DDL
*before* acquiring, then claimed a failed acquisition writes nothing beyond `mkdir`; both are
corrected using experiment 2. §4.4 step 2 now fixes the order **open → connection-local
`busy_timeout` → `BEGIN IMMEDIATE`, with no DDL at all**, because a write lock needs no schema, and
states exactly what may exist after a failed acquisition: `.bridge/`, a 0-byte `state.lockdb`, and
possibly a transient journal belonging to some holder's open transaction — coordination
infrastructure only, never a marker, owner file, database, binding, domain row or ownership. §1.4
replaces the earlier "hot journal left behind" phrasing with what was actually observed at each
step, including that the journal disappears after a clean end, and keeps `immutable` unused. On the
filesystem question, §13 now states a **documented precondition** — the state directory must be on
a local filesystem with working POSIX advisory locking; network and FUSE mounts are unverified and
unsupported — and withdraws revision 5's claim that broken advisory locking automatically yields
`state_locked`, since a filesystem that accepts but does not enforce locks cannot be detected from
inside the protocol. Reported lock errors (`SQLITE_BUSY`, lock I/O errors) still fail closed. No
filesystem diagnostics, probe tooling or installer was added.
