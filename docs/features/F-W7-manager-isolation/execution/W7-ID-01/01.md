## Problems and resolutions

- *How can a resumed manager be told apart from a second one, when `codex` gives an MCP server no
  session identity?* The startup role (`--caller`) is the only identity the server has today
  (`server.ts:73-90`, `tools.ts:115-125`), and `FeatureWorkflow.owned` compares the literal
  string `codex` (`feature-workflow.ts:25-30,72`). Resolved with a bridge-issued public session id
  plus a private attach token: a restarted session still holds the token in its conversation, a
  different session never does, so restart and takeover are structurally distinct.
- *Can the manager's native Codex session id be captured automatically?* The `codex` 0.154 binary
  carries `CODEX_THREAD_ID` beside its shell-exec environment setup, with no evidence it reaches
  MCP servers; a nested launch would also inherit an outer session's value. Resolved by making the
  native id explicitly supplied and advisory, with the token as the actual guarantee, and by a
  static test forbidding session-file/cwd/env sniffing in product sources.
- *Where can the guard be enforced without a TOCTOU gap for asynchronous operations?* Resolved by
  checking authority inside the existing reservation transactions
  (`orchestrator.ts:119-135`, `feature-workflow.ts:123-140`, `orchestrator.ts:520`) rather than
  before them, so a takeover that commits mid-reservation rolls the round back.
- *How is a copied or shared database detected without mutating it?* `ControlPlane.open` currently
  opens and migrates anything it is given (`control-plane.ts:74-88`, `sqlite-store.ts:226-277`).
  Resolved with a read-only preflight of `workspace_binding` before any DDL, plus a
  `.bridge/workspace.json` marker that also catches a *second* database for one worktree.
- *Liveness of an old manager process.* Rejected heartbeat/pid/TTL heuristics as guessing; fencing
  is by identity (latest attach wins, older instance refused with `MANAGER_FENCED`).
- **Unresolved: the round package cannot be exported.**
  `feature_exchange.py:118-121` requires every task registered in `feature.json` to be a Markdown
  path under `work-items/`, while this feature registers `docs/tasks/wave7-identity-01.md` and
  `docs/tasks/wave7-identity-02.md` — the conscious no-Yumi fallback recorded in `design.md`
  ("Brak Yumi w repo: taski Markdown w `docs/tasks/` są świadomym fallbackiem"). The exporter
  therefore fails before writing anything:
  `feature-exchange: Task must be a Markdown path under work-items/: docs/tasks/wave7-identity-01.md`
  (exit 1). `export` has no flag to relax this (`--repo --feature --purpose --output --base
  --head` only), and `verify` applies the same rule to the manifest (`feature_exchange.py:216`).
  Every possible fix is outside this round's write scope — `feature.json` and the task files are
  coordinator-owned, and `.agents/skills/feature-exchange/scripts/feature_exchange.py` is shared
  tooling — so no package was produced and no workaround was attempted.
