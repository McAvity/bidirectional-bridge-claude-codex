## Problems and resolutions

Per-finding disposition:

**R02-01 — package blocked: resolved (by the coordinator, outside this scope).** Tasks are
canonically `work-items/W7-ID-01.md`/`W7-ID-02.md`, which is what `feature_exchange.py:118-121`
requires; `docs/tasks/*` remain pointers. I neither moved tasks nor touched the exporter. Export
and verify now pass (Validation).

**R02-02 — unguarded real mutations: resolved.** Re-read confirmed the review: `ControlPlane.recover`
(`control-plane.ts:135`) calls `leases.reapExpired`, which writes lease rows and `lease.expired`
events (`lease-manager.ts:236-258`), and `lifecycle.ts:59` runs it on every process boot;
`FeatureWorkflow.get` → `refresh` → `save` writes the feature row and a `FEATURE_UPDATED` event
(`feature-workflow.ts:32-40,43-69`). Contract §5.2 now defines five operation classes (P/A/L/F/R),
reclassifies both paths, and specifies three code changes: `get` splits into pure `deriveState`
and persisting `reconcile` (reconciliation only for the attached manager, with a `reconciled`
flag); boot uses a new pure `inspectRecovery()` and only logs; `bridge_recover` is report-first and
reaps solely for the attached manager. The safety argument is grounded, not asserted: lease
liveness is a wall-clock comparison in `isLive` (`lease-manager.ts:53-54`) applied by
`findConflicts`, `acquire`, `renew`, `release` and `listLive` (`78,135-138,160,192,259-261`), and
`lease-manager.ts:233-235` itself calls the reaping cosmetic — so deferring it changes no conflict
outcome. §5.3 states the transaction boundary for each class. New tests F-01 (foreign and fenced
process: full row/event/SHA-256 fingerprint unchanged across boot plus every pure read, each
guarded tool refused, expired-but-unreaped lease still treated as dead) and F-02 (attached
manager does reap and reconcile; derived state identical for everyone).

**R02-03 — legacy adoption weakened AC-04: resolved.** Automatic adoption is withdrawn. §10 is
fail-closed: a legacy database with history is rejected (`unbound_legacy_state`) with nothing
written, migrated or deleted; only a provably empty legacy database binds automatically. Explicit
adoption is a separate operation (`--adopt-legacy-state` plus a mandatory `--adopt-reason`) that
refuses when a binding exists and records durable provenance (adopted root, git dir, database
path, legacy schema version, per-table row counts, operator reason) in `workspace_binding` and a
`workspace.adopted` event. The revision-1 argument from Claude's cwd-keyed session lookup is
removed from the protection story entirely (V-2 demoted to an implementation note). New tests
I-12b (copied legacy `waiting_user` feature, and a feature with no rounds and therefore no handle
— both rejected) and I-12c (adoption path and its refusals).

**R02-04 — ineffective moved-worktree advice: resolved.** The old "delete `workspace.json`"
remedy is removed and §4.5 explicitly documents that it cannot work, because the binding row
inside the database still carries the old root and the step-5 preflight rejects the startup
regardless of the marker. Two non-destructive procedures replace it: move the worktree back to the
recorded root (printed in the error), or archive `.bridge` by renaming it and start fresh at the
new path, with the consequence for existing features stated. A rebind command stays out of v1.
Tests I-09a/I-09b assert that the documented remedies actually work, including that deleting only
the marker still rejects.

**R02-05 — native identity and token durability: progress, with one escalation.** §9 now names the
source (explicit tool argument only; never env, cwd or session files, with the reason
`CODEX_THREAD_ID` is rejected: unverified for MCP servers and inherited by nested launches),
the custody model (token returned once, re-readable only by the attached instance, surfaced to the
user as the restart credential, with a non-capability custody hint at
`.bridge/manager/current.json` that identifies the session without granting attach), and the
missing-data behaviour (stop: no implicit claim while a session is active, no newest-session
resume, no silent takeover). §9.3 separates what the bridge guarantees and tests (M-02/M-03/M-04/
M-05/N-01/N-04) from what it cannot verify, and states that the static no-scanning grep (N-03) is
only a supporting check. I did **not** decide the remainder: whether AC-03 should require the
bridge itself to verify native session identity, or whether machine-local token custody should be
added for unattended restarts, is escalated as **Q-02** in §16 with a recommendation (keep the
split guarantee; do not add a local credential file, since any local process could read it).

**R02-06 — provenance: resolved** in this ledger's Provenance section; `execution/W7-ID-01/01.md`
was not edited.

**Concurrent bootstrap of two worktrees sharing a not-yet-created `--db`: resolved.** The review
is correct that a pre-DDL preflight cannot help when the file does not exist yet — both processes
would pass it and `SqliteStateStore`'s constructor creates the file and runs DDL
(`sqlite-store.ts:226-246`). §4.1 adds a third record, the database owner sidecar
`<database>.owner`, created with an atomic `linkSync`, and §4.2 fixes the order: marker (own
worktree, so racing same-worktree processes settle on one `workspace_id`) → sidecar claim →
read-only preflight → open/DDL → binding row in `BEGIN IMMEDIATE` → sidecar/marker completion.
Only the sidecar winner may create the database file. §4.3 tabulates each race and its outcome,
and test I-13 runs two real processes from two different worktrees against one non-existent `--db`
concurrently, asserting one success, a non-zero exit with `database_owned_elsewhere` for the
loser, and that neither the database nor its `-wal` is created by the loser. I-14 covers a sidecar
that disagrees with the binding row (record C wins). The marker's `database` field is now written
only after a successful bind, so a rejected startup cannot poison the next attempt.
