# Proponowane rozstrzygnięcie Q-02 — natywna tożsamość managera

Status: proposed; brak decyzji użytkownika. Wejście: reviews/03-corrections.md, kontrakt r2 z 08d01c7 i brief AC-03. Poprawki R02 zrobiły postęp, ale wykonawca proponuje zmianę granicy gwarancji.

Rekomendacja koordynatora: zachować pierwotny wymóg dokładnego przypisania natywnej sesji i najpierw ustalić oraz zweryfikować zaufane źródło tej tożsamości. Nie uznawać niezweryfikowanego kanału za niemożliwy. Wariant ręczny (ID sesji i token dostarczane/przechowywane przez użytkownika) może być wybrany tylko jako jawna akceptacja ograniczonej gwarancji i obowiązku obsługi po stronie operatora; sam token/plik lokalny nie dowodzi natywnej sesji.

Q-02 dla użytkownika: Czy zachowujemy wymóg potwierdzania dokładnej natywnej sesji managera i najpierw weryfikujemy zaufane źródło jej tożsamości (rekomenduję), czy dopuszczasz wariant ręczny: sam wskazujesz sesję Codexa i przechowujesz token, a bridge sprawdza token bez potwierdzania natywnej tożsamości sesji?

Do czasu rzeczywistej odpowiedzi: bez nowych rund, recovery, implementacji ani przyjęcia featura. R03-02/03 są zwykłymi korektami kontraktu pozostającymi do wykonania po rozstrzygnięciu; nie wymagają obniżenia AC. Historia, dostawa i oryginalna paczka pozostają zachowane.
