## Problems and resolutions

- R16-N1 confirmed and sharpened: `commit_or_diff` is forced to `null` (runner 1044) and
  `verification_snapshot`/`reproduction_snapshot` are **not** stored in the deliverable
  either (only validated, runner 1002–1019). Unknown JSON keys are dropped. The only
  always-retained executor channel is the start of `summary` (≤ 4000 chars). Resolution:
  a single `DELIVERY=local-v1 …` first line, mirroring the existing `PACKAGE=` convention.
- Blocker path replaces `recommended_next_action` (adapter 365–366) and prepends the
  blocker to `remaining_risks`; the contract does not rely on either for delivery data.
- Malformed verification entries vanish silently (runner 503–530): the contract makes the
  coordinator compare the ledger's check list with `verification_results`.
- `remaining_risks` items have a 2000-char schema limit (schemas.ts 354); an oversize item
  would fail `submit`. The dirty-path disclosure is therefore bounded, overflow to the ledger.
- The worktree has no `node_modules`; the probe ran on a `git archive HEAD` export of the
  base with the main checkout's dependencies symlinked (vitest aliases `@bridge/*` to the
  exported sources, so the tested code is the base's code).

## Deviations and proposals

- Implementation choice: `WORKTREE=clean|dirty:N` plus bounded `UNCOMMITTED own|preexisting`
  risk entries rather than listing paths in `summary`, to keep the line short and within limits.
- Proposal for W16-02: executor instructions emit the delivery line as `summary` line 1,
  commit the ledger before reading `HEAD`, and rerun checks if code changes afterwards.
- No API expansion is proposed; the existing `summary` + Git is sufficient. A later
  `commit_or_diff` population would be a separate decision, not needed here.
