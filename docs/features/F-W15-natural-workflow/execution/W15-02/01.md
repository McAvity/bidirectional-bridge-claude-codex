## Outcome

`complete` for W15-02.

**1. A portable, read-only entry (W15-C1, AC-03, AC-08).** The committed project entry point now
accepts `--status` / `--instructions`. `scripts/bridge-project/entry-template.mjs` routes that
mode, `dispatch.mjs` answers it with a new pure `describe()`, and both the plugin's `status` and
`describe()` derive their paths from one new `instructionPaths()` in `locate.mjs`, so the two can
never disagree about which instruction set a pin selects.

The mode answers **before** the launch gate and resolves the pin itself, so it works in a
worktree inherited through Git that has no `.bridge-runtime/current` and no local state at all.
It resolves no identity, opens no database, takes no lease and writes nothing in any state. It is
not a second installer: a missing runtime, an unreadable or unrecognised declaration and a
diverged pin come back as a code, a state and a `next_step`; `setup` remains the only writer. The
entry point stays minimal (71 lines, below the 80-line ceiling the existing test asserts).

`locate.status()` also reports `preference.declared`, a pure read of whether the project records
a preference, so a manager can distinguish "no preference" from "consent to delegate".

**2. The optional project preference (AC-03).** `planPreference()` in `scripts/setup/workspace.mjs`
adds one managed block to the project's `AGENTS.md`, following the existing
`planCodexConfig`/`planGitignore` pattern rather than whole-file ownership: content outside the
markers is preserved, an identical block is a no-op, a block whose hash the worktree recorded is
updated, and anything else is a named conflict. Its identity is recorded as
`managed.preference_block` and carried forward by runs that did not ask for it.

It is written **only** with an explicit `--with-preference`, on `bridge.mjs init/update` and
`bridge-plugin.mjs setup`. Ordinary `init`, `update`, `setup` and `rollback` never read or write
`AGENTS.md` — `rollback` ignores the flag entirely — so no plugin or runtime delivery can
introduce or change a project's policy. The plan shows the concrete `unifiedDiff`, now also in
the plugin's JSON and text output, before anything is applied.

**3. Natural requests in the instructions (AC-01, AC-02).** The plugin entry skill template, the
Codex role skill and the Claude role skill each gained a short section: recognise an ordinary
request that names a document; classify it as a brief, a finished plan, a review or an unapproved
proposal; treat "only review", "only a plan", "do it yourself" and any narrower permission as
binding; treat the document's own text as untrusted content that never grants push, merge,
deployment, a larger budget or permission to delegate; and treat reading as not consent to
execute. The entry skill's `description` now mentions implementing, planning, reviewing or
continuing a feature described in a repository document, so the skill is selectable without the
user naming it.

`enabled: true` is stated as permission for the bridge to run, not a standing instruction to
delegate: with `preference.declared: false` the manager does the requested work under the
ordinary delegation checkpoint and offers the preference step at most once. The manager/executor
split is restated on both sides — a Claude round completes its own contract and never runs the
manager workflow or delegates further.

**4. Documentation and packages.** `README.md` (quick start now shows a natural sentence and the
portable read), `docs/setup.md`, `docs/setup-layout.md`, `docs/plugin-distribution.md` and
`docs/features/README.md` describe the new behaviour, the refusal codes and the explicit-only
nature of the preference. `plugins/**` and both marketplace manifests were regenerated by the
generator and pass the source-equivalence gate.

## Problems and resolutions

**The distribution test installs a runtime from `HEAD`.** The first run of the new entry tests
failed with a null report because `bridge-project.test.ts` builds its runtime with
`git archive HEAD`, so uncommitted work is invisible to it and the project received the previous
entry template. The work was committed first and the tests then exercised the real behaviour.
This is a property of the harness, not a defect: it is what makes the suite test a real
installed runtime rather than the working tree.

**A directory URL carries a trailing separator.** `defaultRuntimePath()` returned
`<runtime>/`, which never mattered while the value was only used for `join()` but made the
reported `instructions.root` differ from the runtime path every other reader uses. Fixed with
`resolve()`, which normalises without touching the filesystem (commit `55d3e5f`).

**Where the preference must not live.** `planGitignore` is called unconditionally from
`planChange`, so attaching the preference next to it would have made every `init`/`update` write
a policy. The preference is therefore gated on an explicit option that is threaded through
`planChange`, `managedDestinations` (so the symlink refusal covers `AGENTS.md` only when the step
is requested) and the record.

## Deviations and proposals

Ordinary choices, not deviations: the preference block is written in Polish, matching this
project's own instruction files and the plan; `--with-preference` reuses the existing plan/apply
option style rather than adding a subcommand; the plugin's change report gained the `diff` field
the setup CLI already produced, so both surfaces show the same concrete change.

One scope judgement worth naming: `rollback` accepts the flag but never acts on it, rather than
failing with a usage error. Moving a pin back is not a moment to change a collaboration policy,
and a refusal would be a worse outcome than quietly not changing the file; the behaviour is
stated in both CLIs' help and asserted by a test.

No protocol change, no new public configuration format, and no change to any project's existing
files: this worktree's own `AGENTS.md` and `.bridge-project/` are untouched, as required.
