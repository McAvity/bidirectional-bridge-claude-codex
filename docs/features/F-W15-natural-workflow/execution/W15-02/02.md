## Outcome

`complete`. Each finding is fixed in the canonical source, not described away.

**I1 — the preference named an entry point the legacy profile never installs.** `planChange` now
refuses the option by name when `profile !== "dispatcher"`, with
`PREFERENCE_REQUIRES_DISPATCHER` and a next step pointing at the dispatcher setup. The refusal
happens before anything is planned, so nothing is written. The installer was not extended and no
project is re-pinned. `docs/setup.md` now documents the refusal instead of the behaviour it could
not deliver. The regression asserts the refusal *and* that the named entry point genuinely does
not exist in a legacy worktree; on the dispatcher side a second regression extracts the path from
the written block, runs it, and requires a successful report — so the block is verified by
execution, not by matching text.

**I2 — a new AGENTS.md showed no diff.** The create branch of `planPreference` now carries
`previous: Buffer.alloc(0)`, which is what both CLIs diff against, so a project with no
`AGENTS.md` sees the whole proposed block instead of a file name. It is deliberately not marked
`userFile`: there are no bytes of the user's to back up. The regression covers both an absent and
an empty file and asserts the diff contains the proposed text and the entry-point line.

**I3 — the plugin ignored the pinned commit.** `locate.status` now compares
`manifest.source.commit` with the declaration and classifies a difference as
`pin-commit-mismatch`, which suppresses `instructions` and produces a concrete `next_step`.
`describe()` in the dispatcher was reduced to that single classification plus the instruction
paths of the runtime it was loaded from, so the plugin and the entry point can no longer disagree:
the regression drives both against the same tampered declaration and requires the same state, the
same absent instructions and the identical `next_step`, with nothing written.

**I4 — a marker pair was presented as consent.** `hasPreference` is replaced by
`preferenceState`, which reports `managed_block: known | modified | absent` — `known` only for the
exact block this runtime writes — together with `authoritative: false` and a note saying that a
rewritten block may say the opposite, that a preference in prose outside the markers is equally
valid, and that a narrower instruction or a prohibition always wins. The `declared` boolean is
gone from the payload, from both role skills and from the docs. The regression puts
"Never delegate implementation." between the markers and requires `modified`, `authoritative:
false` and the absence of `declared`.

**I5 — the entry skill carried its own copy of the workflow.** Section 0 of the template no longer
classifies brief / plan / review / unapproved proposal. It keeps the trigger and the boundaries
that are about consent and setup rather than workflow, and directs the reader to
`instructions.codex_role_skill`. The classification stays canonical in the pinned role skill.
Beyond documenting that `--status` needs a runtime that ships it, the entry point now *enforces*
it: it checks that the loaded dispatcher exports the read-only mode and answers
`RUNTIME_WITHOUT_STATUS` rather than falling through to a normal MCP start on an older runtime.
The regression asserts the package no longer carries the classification text.

## Problems and resolutions

**The refusal changed what the legacy tests could assert.** The three preference behaviours
previously exercised through `bridge.mjs init --with-preference` cannot exist there any more, so
that suite now proves the refusal and the untouched bytes, and the full behaviour (diff,
idempotence, preservation, `PREFERENCE_MODIFIED`, `PREFERENCE_CONFLICT`, symlink) is exercised on
the dispatcher/plugin surface where the feature actually lives. That is coverage moved to the real
surface, not coverage dropped.

**The entry point's line ceiling.** The existing test keeps `entry.mjs` under 80 lines. Adding the
older-runtime guard pushed it to 80; the comments were tightened rather than the guard dropped,
and the file is 79 lines including the final newline.

## Validation

All checks ran on the final snapshot of this round; the command list and results are in
[W15-03/01.md](../W15-03/01.md) to avoid repeating them in three ledgers. The suites that cover
this ledger are the 12 cases of `bridge-project.test.ts -t "reports without serving"` and the 2
cases of `setup.test.ts -t "optional project preference"`, both against a real installed runtime,
real git worktrees and the real committed entry point.

Limits: no model was involved, so the instruction changes are verified as text, as path selection
and as process behaviour, never as model behaviour. `RUNTIME_WITHOUT_STATUS` is asserted through
the guard's presence and the package text, not by installing a genuinely older runtime and running
the flag against it — that would need a second historical build in the suite.
