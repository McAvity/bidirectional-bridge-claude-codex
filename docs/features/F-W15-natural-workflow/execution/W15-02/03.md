# Ledger W15-02 / attempt 03 — correction W15-I8

## Scope / Inputs

One finding only. Authority: [decisions/01.md](../../decisions/01.md); direction from the latest
section of [reviews/02-implementation.md](../../reviews/02-implementation.md), read at this round's
base `9cf439d42a4454688e553860265540d2819ad737`. Attempts 01 and 02 are preserved unchanged.

The reported case: a current plugin, a project declaring an **older** installed runtime
(`ff225e5`, which is also the current release pin), and `setup --with-preference --yes`. The run
succeeded and wrote an `AGENTS.md` telling the reader to run `.bridge-project/entry.mjs --status`.
But `setup` copies the entry point **from the target runtime**, and that runtime's template
predates the read-only mode: it ignores the flag, falls through to the ordinary MCP path and ends
at EOF with no status JSON. The preference named a read that never answers.

## Outcome

`complete` for W15-I8. No other finding was touched.

**The precondition, one level deeper than I1.** `planChange` already refused the option for the
legacy profile, because that profile installs no `.bridge-project/entry.mjs` at all. The same rule
now applies to the dispatcher profile when the *target* cannot serve the read:
`PREFERENCE_UNSUPPORTED_RUNTIME`, raised before anything is planned or written, with the runtime
id in the message and a next step that says the pin is never moved for the user.

**The capability is read off the target, not inferred.** `servesProjectEntryStatus(runtime)` in
`scripts/setup/runtime.mjs` reads two files of the target runtime and requires both halves of the
path to be present: its entry template must route `--status`, and the dispatcher that template
loads must export the pure `describe` the entry point calls. It executes nothing — a plan must not
import a foreign runtime's code — and it never consults the version of the plugin doing the
writing, which is exactly the mistake the review warned against, since an old pin is the common
case rather than the exception.

**Step-back, as the review asked.** This is the third time the class "the preference names an
entry that does not work" appeared (I1, I5, I8). The simplest rule that removes the class is: one
correct entry for the selected runtime, and refuse to write a preference that would not have one.
So there is no fallback that picks a different skill set or a different runtime, no automatic pin
change, no second installer and no MCP change — only a precondition and a named refusal. The
classification stays in its single existing place and the setup machinery is untouched otherwise.

**The regression goes through the public path.** `bridge-project.test.ts` builds a historical
runtime from the commit **before** the mode existed — resolved from this repository's own history
rather than hardcoded — into the suite's temporary home, and asserts up front that its entry
template really has no `--status`. It then runs the real `bridge-plugin.mjs setup --yes --to
<historical id> --with-preference` and requires: exit 1, `ok: false`, `applied: false`, the
refusal code, the runtime id in the message, and **zero project writes** — the directory listing
is byte-for-byte what it was, with no declaration, no entry point and no `AGENTS.md`. It then
prepares the same project on that same historical runtime *without* the preference, which stays
allowed, and runs the entry point the preference would have named: its output does not parse as
JSON and contains no `instructions`. A second case shows a supported target still records the
preference and that the named entry point answers with the pinned runtime's instruction root.

The machine's installed runtimes are read but never modified: the historical runtime is built into
the suite's own temporary home, and the active `0.2.0-ff225e550966` was only read.

## Problems and resolutions

The natural first instinct — import the target's dispatcher and check `typeof describe` the way
the entry point does — was rejected. A plan is a read; importing an arbitrary older runtime's code
inside it would run foreign code during a dry run. Reading the two files gives the same answer with
no execution, and the comment says exactly what it checks so a future reader can see its limits.

## Validation

Recorded for the whole round in [W15-04/02.md](../W15-04/02.md). The focused evidence for this
ledger is `npx vitest run scripts/bridge-project/bridge-project.test.ts -t "cannot serve it"` —
exit 0, 2 passed, 64 skipped.

Limit of this evidence: the probe is a source check of the target runtime, so a future runtime that
implements the mode under different names would be classified as unsupported and refused. That is
the safe direction — a false refusal costs a message, a false acceptance writes a broken
instruction — and it is stated here rather than left implicit.
