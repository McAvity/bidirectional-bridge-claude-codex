## Outcome

`complete`. Both carried findings are closed in the canonical document, in place.

**W15-C2 — where the intent file lives.** Round 2 put it in `.bridge/intent/`. That is wrong for a
concrete, checkable reason: `classifyNativeState` treats a `.bridge` directory without
`workspace.json` as unexplained and `assertPristineStateDirectory` refuses unknown files, so
writing the intent before the bootstrap would block the very bootstrap it precedes. §3 now places
it in this worktree's **existing** private exchange namespace —
`<namespace>/intents/<op>-<key>.json`, where `<namespace>` is what `feature_exchange.py namespace`
already prints as a pure read. That space is per worktree, outside the repository, never
committed, and needs no new location, format or script change. The section states the remaining
requirements the review asked for: one file, written atomically (temp file plus rename) before the
call leaves; durable until the operation closes; a missing or unreadable file is a blocker, not a
reconstruction; identifier updates during `running` go there, so nothing commits inside an open
round; and the file records intent only — the bridge remains the sole authority on acceptance.
No new state machine and no second state store: one file plus the existing replay.

**W15-C4 — the contradictory advice removed in place.** The main §4 table still told a manager to
reconcile a lost root task with `bridge_list_tasks({owner: "codex"})` plus `objective`/`scope`,
and still called an unchanged `predecessor` proof that a reservation had not landed. Both cells
are rewritten rather than annotated with another exception: the root row now says plainly that
**no read decides this** — an unclaimed task has no owner and objective/scope is not an identity —
and that re-sending the identical call with the persisted key is the whole mechanism; the round
row keeps "a new id proves acceptance" but states that an unchanged `predecessor` is an
observation from one moment, with the identical replay as the single correct move in both cases.
Rule 2 below the table was rewritten the same way instead of carrying a "W15-C4 note" appended to
the old claim.

## Problems and resolutions

One factual claim in §4 turned out to be wrong, and the W15-03 regression is what found it. The
"Claim + WORKING" row asserted that `WORKING → WORKING` fails with `ILLEGAL_TRANSITION` because
that pair is absent from `ALLOWED_TRANSITIONS`. `TaskService.transition` short-circuits with
`if (task.state === input.to) return task` *before* the legality check, so repeating the step is
safe with or without a key. The row is corrected and marked, and the test now pins the real
behaviour. The original claim came from reading the transition table without reading the function
that consults it — which is exactly the failure mode the review's "check it on the real harness"
requirement exists to catch.
