## Problems and resolutions

**Mutations must not be assumed idempotent — and several are not.** Verified against source:

- `bridge_create_task` is idempotent only when the caller supplies `idempotency_key`
  (`task-service.ts:80-95`); without it a repeat creates a second task with a fresh ID.
- `bridge_set_state` to `WORKING` is not repeatable without a key: `WORKING→WORKING` is absent from
  `ALLOWED_TRANSITIONS` (`shared/protocol/src/types.ts:42`).
- `bridge_feature_create` takes **no** `idempotency_key` argument (`tools.ts:282`) but is naturally
  idempotent per `feature_id`, refusing a different owner/parent with `IDEMPOTENCY_MISMATCH`
  (`feature-workflow.ts:122-127`).
- `bridge_resume_delegated_task` accepts the key as optional in general and requires it only with
  `message` or `recover_timeout` (`orchestrator.ts:1359-1377`); without a key, only an in-process
  map dedupes (`:559-577`), which a restart loses.

**The "interrupted after reservation, before the manager learns the task id" case is solvable with
no new state.** The round's task creation, the feature row update (`latest_task_id`, `task_ids`,
`active_task_id`, `state`) and the idempotency record all commit in one transaction
(`orchestrator.ts:154-171` invoking `feature-workflow.ts:186-213`), so `feature.task_ids` compared
against the checkpoint's `predecessor` is an exact discriminator.

**Recovery replay reports "still running" as an error, not a success.** `replayRecovery` throws
`ILLEGAL_TRANSITION` "recovery attempt N is already active" while the recovered attempt is open
(`orchestrator.ts:1309-1315`). The design records that this is an acceptance signal, because
treating it as a failure would push a manager toward a duplicate operation.

**Class R reads are free after an interruption.** They write nothing and do not require being the
active manager instance (`tools.ts:230-235`, `identity-runtime.ts:207-217`,
`feature-workflow.ts:60-84`), so repeated interruption during reconciliation is harmless. Mutations
after a crash still need `bridge_manager_resume_instance`, or an explicit takeover from a different
Codex thread (`manager-registry.ts:210-221`, `:260-281`).

## Deviations and proposals

Ordinary choices, not deviations: `design.md` is written in Polish, matching `brief.md`,
`decisions/01.md`, `docs/plans/wave15.md` and the earlier `F-W13-diagnostics/design.md`; this
ledger is in English, matching the earlier ledgers in that feature. The checkpoint is proposed as
an addition to the existing per-task ledger plus a new `execution/coordination/NN.md` for
coordinator-only operations that belong to no round — no second state store, per plan line 129.

Proposals requiring a decision outside this round:

- **G-2 (protocol gap)** — a round orphaned before its execution handle is persisted has no
  authorized exit: recovery needs the handle (`orchestrator.ts:675-682`), a new round is refused
  while `active_task_id` is set (`feature-workflow.ts:169-170`), `waitUser` is refused while the
  attempt has not ended (`:262`) and `accept` needs `awaiting_review` (`:292`). Three alternatives
  are recorded in `design.md` §5; the recommendation is a separate, explicitly authorized
  "abandon stranded attempt" operation. **Not implemented here**; W15-02/03 do not depend on it.
- **G-3** — the round request hash covers the presence of server-side callback keys, so a round key
  cannot be replayed across a runtime/profile change. W15 adopts the documentation-only mitigation;
  changing the hash input is a public idempotency-contract change needing its own resolution.
- **G-1** — an orphaned round reports `running` indefinitely because `derive`/`refresh` treat any
  `HELD` lease row as liveness (`feature-workflow.ts:64-72`, `store/sqlite-store.ts:709-714`) and
  nothing expires stale leases while identity is enforced (`tools.ts:1096`, `lifecycle.ts:100-102`).
  Resolvable today by combining `bridge_recover` (pure) with `bridge_get_task`; W15-03 documents
  the rule. No protocol change proposed.
- **G-4** — no read maps an idempotency key back to a `task.create`; `bridge_read_events` filters
  only by `after`/`task_id`/`limit` (`tools.ts:1074-1078`). Worked around by matching the
  checkpoint's exact objective and scope. No protocol change proposed.
