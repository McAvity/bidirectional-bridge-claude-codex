## Outcome

`complete`. All four required findings are resolved in `design.md`; each correction is marked in
the document with a short `Korekta W15-Cn` note so a reviewer can see what changed and why.

**W15-C1 — entry in a pristine worktree.** §1 rewritten. The claim that a plugin-less project can
rely on `.bridge-runtime/current` was wrong: an inherited worktree is `inherited-pristine` and has
no such path, and a pure read must not create one. The corrected design specifies the minimal
read-only mode of the *existing* project entry point and dispatcher, which resolves the pin
itself, derives the instruction paths from the pinned runtime directory, and is not a second
installer. §2 now points the `AGENTS.md` preference at that portable read instead of a local path.
This correction is implemented in the same round (W15-02).

**W15-C2 — a checkpoint that can actually be written and replayed.** §3 rewritten around two
carriers with different roles: a local, git-ignored intent file written *before* the first
mutation — which is the only thing possible when no root task, ownership or lease exists yet —
and the coordinator's own ledger entry, written only once ownership and a lease exist and no
round is open. The executor's ledger is never touched by the coordinator. The intent file stores
the exact arguments, because a replay needs the identical request; a hash only detects
divergence. Missing exact data is now explicitly a blocker rather than a reconstruction guessed
from a hash. Identifier updates during `running` go to the local file, so they neither commit
during an open round nor put manager changes into the executor's package. The public/local data
split is stated: no private contracts, user answers, transcripts, handles or evidence content in
a commit. The intent file is explicitly *not* a competing state store: it never decides whether
an operation was accepted.

**W15-C3 — no substitute feature.** The G-2 alternative "continue under a new `feature_id`" is
withdrawn; it was a way around the recovery boundary. The corrected §5 states the actual
behaviour: a missing execution handle is a real limit of strict resume, so the manager stops with
a concrete diagnosis (task, attempt, reason, feature state, termination evidence), preserves the
evidence and asks the user. No new Claude session, no replacement task, no new feature id. The
withdrawn "abandon stranded attempt" operation is recorded as not implemented and not proposed as
W15 work, since it would be a public protocol change. The section now separates two events that
are easy to conflate: losing the manager's response does not prove the server or worker died —
only the server process dying orphans an attempt — and W15-03 must test them separately.

**W15-C4 — strict discrimination and corrected scenarios.** G-4 rewritten: a root task lost
before `claim` has `owner: null` and therefore never appears in `bridge_list_tasks({owner:
"codex"})`, and `objective`+`scope` is not an identity. The only admissible discriminator is an
identical `bridge_create_task` with the persisted key. §4 gained the rule that an unchanged
`predecessor` is an observation from one moment, not proof of non-acceptance — a request still in
flight may commit its reservation right after the read — so the only correct reaction is an
identical replay, never a new key. The scenario table is corrected: S-05 is split into S-05a (an
active worker refuses a new key, so no duplicate arises there) and S-05b (after `DONE` a new key
really does start a second round — the case that justifies the rule); S-08 now requires a
recoverable state after the first attempt, because a `DONE` task is refused by
`assertRecoverable`; S-10 is split into a lost response with a live server and a dead server with
no persisted handle.

## Problems and resolutions

The review's C2 exposed a genuine ordering impossibility in the first design, not a wording
problem: a coordinator cannot hold a lease before the root task it would lease against exists.
Resolving it required admitting a second, local, non-committed carrier rather than forcing
everything into the repository ledger. The design now says why that is not a second state store:
it records intent and arguments, and it never decides acceptance, which stays with the bridge.

Nothing else was reinterpreted. No acceptance criterion, plan scope or protocol behaviour was
changed by these corrections.
