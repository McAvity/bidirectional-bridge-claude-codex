## Outcome

`complete` for W15-03.

**1. "Continue" in the canonical instructions.** `bridge-loop.md` replaces its short interruption
section with the rule the plan asks for: after capacity, a lost response, a disconnect or a
restart, *continue* alone is enough, and the manager must not ask the user for identifiers durable
state already holds. The order is fixed — read your own Git state and intent files, then the
bridge's pure reads, and only then act — followed by a table: `running` waits, `awaiting_review`
collects and reviews, `blocked` resumes the same task with its key, `waiting_user` waits for a
real answer, genuine uncertainty re-sends the **identical** request, a foreign manager or an
ambiguous session asks, and an exhausted budget is reported rather than renewed. The round
contract's `idempotency_key` guidance is corrected in place: choose the key once, write it to the
intent file, and after an interruption take it from there — recomputing `len(task_ids) + 1` after
a reservation has landed is precisely what duplicates a round. `.codex/skills/using-bridge`
carries a short version with the same rules and points at the full table.

The bootstrap steps are covered, not only rounds: the identical `bridge_create_task` with the
persisted key is the only way to tell whether a root exists, because one lost before
`bridge_claim_task` has no owner; claim and the WORKING transition are safe to repeat;
`bridge_feature_create` is idempotent per feature id; recovery without a key is not a retry.

**2. The intent file.** One JSON file per operation in this worktree's existing exchange
namespace (`<namespace>/intents/`), written atomically before the call leaves, never in `.bridge/`
or `.bridge-runtime/`. No new helper was needed and none was added: the namespace already has a
pure read (`feature_exchange.py namespace`), the replay already exists, and there is no second
state store or state machine.

**3. Regressions on real bridge state.** `shared/control-plane/src/wave15-continuation.test.ts`
runs the real `ControlPlane`, `Orchestrator` and `FeatureWorkflow` against a real SQLite file;
only the agent runtime is a fixture adapter, so reservations, idempotency records, attempts,
leases and events are the product's own. Closing and reopening the store is the manager restart.
Nine cases, each asserting what a duplicate would disturb — task count, attempt count, worker
launch count, identity, key, the contract that reached the worker, event history and budget:

| Case | Interruption | What it pins |
| --- | --- | --- |
| before send | nothing reserved | one task, one launch; the contract and `max_turns` that reached the worker |
| accepted, response lost | gated worker, restart | replay returns the same task id, launches stay 1; a new key is refused while active; same key with different arguments is `IDEMPOTENCY_MISMATCH` |
| repeated reconciliation | three restarts, three replays | one task, one launch, one `task.created` event |
| done before retrieval | restart after `DONE` | retrieval is a read; then the counterexample — a recomputed key really does start a second round |
| recovery, response lost | gated recovery, restart | `ILLEGAL_TRANSITION` "already active" means accepted; the replay reuses `recovered_attempt`; `max_turns: 48` applied to that attempt only while the stored spec keeps 32; one `recovery.requested` event carrying the key |
| recovery without a key | recoverable state after the attempt | a third attempt really is spent — and a `DONE` task is refused outright |
| lost response vs dead server | live server; then a dead one with no handle | the first is simply collectable; the second stops at "no persisted execution handle" with no new task, attempt or launch |
| waiting_user, foreign, closed | question pending | run and recovery refused, a foreign manager cannot read the feature, answering alone starts nothing |
| interrupted bootstrap | root, claim, state, feature | key replay returns the same root; the keyless twin is unclaimed and invisible to a listing by owner; one state change in the history; a different parent is a mismatch, not a second feature |

`scripts/bridge-project/bridge-project.test.ts` adds the placement evidence the review asked for:
a real pristine inherited worktree with an intent file written into its exchange namespace still
bootstraps normally and leaves the file untouched, while the same file placed in `.bridge/` makes
that bootstrap refuse with `SETUP_STATE_PARTIAL`.

## Problems and resolutions

**A design claim did not survive contact with the real state.** §4 asserted that
`WORKING → WORKING` fails with `ILLEGAL_TRANSITION`, derived from `ALLOWED_TRANSITIONS`.
`TaskService.transition` returns early when the task is already in the requested state, before the
legality check, so the step is safe to repeat. The test now pins the real behaviour, §4 is
corrected and marked, and the instructions say "repeat it" rather than "always pass a key". This
is the concrete value of the review's requirement to check scenarios on real state.

**Concurrency in the fixture.** Reading through a second connection while a gated worker holds the
first is exactly the situation a restarted manager is in, and SQLite handles it; the existing
feature-workflow suite already relied on that, so no new machinery was needed to express a restart.

exercised by the existing identity suites, not re-proved here. No manager code writes intent
files; the carrier is a documented convention with a placement regression. The full `npm test`,
the Python suites and the pilot tests belong to W15-04.
