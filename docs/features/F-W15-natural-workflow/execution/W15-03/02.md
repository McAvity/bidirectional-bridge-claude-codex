### C2 — the replay evidence now depends on the file

`wave15-continuation.test.ts` persists the exact round request, and now also the exact recovery
request, through one atomic write (temp file plus rename) before the call leaves. Every call made
*after* an interruption is rebuilt from a freshly parsed copy of that file — `reload()` then
`fromIntent()` — so nothing the test held in memory can stand in for recovering the request. The
same re-parse happens on each of the three repeated reconciliations, and each iteration re-checks
the key, the contract that reached the worker, the budget and the task/attempt/launch counts. The
recovery case re-parses twice: once while its attempt is still open (where the same key must be
reported as already active) and once after it ended (where it must replay the same reservation),
and it now asserts that the `max_turns` and the message the worker received are the ones the file
holds.

The directory used is the fixture's own temp directory. Where the intent file belongs in
production — this worktree's exchange namespace, never `.bridge/` — is proved separately by the
real bootstrap regressions in `scripts/bridge-project/bridge-project.test.ts`, and the test file
says so rather than implying it covers both.

### I6 — the no-handle boundary, proved on a state that has it

The previous case kept a gated adapter running and a live lease, and accepted
`/lease|persisted execution handle/` — a pattern a lease conflict alone would satisfy. The
replacement builds the precondition through the product's own path (a round whose runtime never
reported a session id and which left the task recoverable) and then **asserts** that precondition
before acting: the task is `BLOCKED`, its single attempt has `execution_handle === null`, there is
no live lease for it, and no adapter is in flight. The expectation is the exact error —
`INVALID_ARGUMENT` with `task <id> attempt 0 has no persisted execution handle` — so a lease
conflict could not produce it. Task, attempt, event, task-state and feature-membership snapshots
are compared before and after, and a second identical call is made to show the refusal is a
boundary rather than a transient failure.

Two limits are now stated in the test file itself and are not claimed away:

- reopening the store is a second connection to the same durable state, which is what a restarted
  manager sees. **It is not an operating-system process kill**, and nothing here kills an MCP
  server, a runtime or a model process;
- an attempt row left *open* by a crash is a further variant this case does not construct. The
  guard under test reads the persisted handle of the task's current attempt and fires before the
  lease check either way, so the boundary it proves is the handle, not the attempt's open state.

The scenario that claimed to cover `waiting_user`, a foreign manager **and** a closed feature is
renamed to what it actually covers, and acceptance gets its own case. That case records the real
behaviour: after `accept`, replaying the stored key still returns the original round and starts
nothing (the replay is answered before the state check), while a *new* key is refused. Its comment
also states that the feature-workflow ownership rule it exercises is not the native Codex
thread/takeover guard, which has its own identity suites.

### I7 — a role contract instead of a byte mirror

`native-launcher.test.ts` required the two `using-bridge` skills to be byte-identical. Wave15
deliberately gives the Codex manager a continuation entry the executor must not carry, so that
assertion could only have been satisfied by copying manager workflow into the worker's skill —
the opposite of the separation. **Nothing was copied.** The assertion is replaced by the contract
that still has to hold, with four checks: the shared material (`agents/**`, `references/**`) stays
byte-identical; both packages carry the same file inventory; both entry skills keep the
role-neutral guards, including "already a delegated worker … do not create a new root or delegate
again" and the round-worker guard; and the manager-only continuation entry appears exactly once,
on the manager side. The whole-package hash walk is kept, not removed.

One assertion was drafted and withdrawn during this work: requiring the Claude skill to be free of
`bridge_manager_status`. It failed, correctly — a Claude session may itself be the manager of a
Codex child, so that material is legitimately shared. The comment now says which part is shared on
purpose and which part must not be.

## Problems and resolutions

The accepted-feature case initially expected a stored-key replay to be refused. It is not:
`FeatureWorkflow.run` answers a replay before checking the feature state, which is what makes a
late duplicated "continue" harmless. The expectation was corrected to the real behaviour rather
than the test being dropped — the same failure mode as the `WORKING → WORKING` claim corrected in
attempt 01, and the same resolution.
